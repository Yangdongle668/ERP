## 2. 高优先级（建议上线前处理）

### 2.1 MySQL 兼容性未纳入自动化测试（缺陷，第一批已处理）

> **已处理**：CI 新增“后端集成测试（MySQL 8）”任务（GitHub Actions `services` 启动 MySQL 8，用环境变量 `SPRING_DATASOURCE_*` 覆盖 H2 连接，全部集成测试再跑一遍）；新增 `SqlReservedWordTest` 检查实体列名 / 表名、迁移脚本列名、SQL 字符串别名不得为 MySQL 8 保留字。首次在 MySQL 上跑全量测试发现并修复了：
> - DATETIME 毫秒被四舍五入（“现在”发布的公告被存成下一秒，登录弹窗查不到）：MySQL 连接串增加 `sendFractionalSeconds=false`（截断）；
> - AI 问数日志、缺料快照等按创建时间排序在同一秒内顺序不稳定：增加 ID 作为次排序。


- 现状：CI 与集成测试只使用 H2（MySQL 模式）。本次 Docker 部署发现以下 3 个实体在 MySQL 下启动即报 SQL 语法错误，已在提交 `7a43268` 修复：
  - `UomDO.precision`
  - `PaymentTermDO.usage`
  - `CodeRuleDO.separator`

  原因是 MyBatis-Plus 生成的列别名是 MySQL 保留字，而 H2 不报错。
- 已用全部 213 个无参 GET 接口对 MySQL 做过冒烟测试，未再发现 SQL 错误。但写入类接口、复杂报表 SQL 仍未系统验证。
- 建议：
  - CI 增加一个使用 MySQL 8 服务容器的集成测试任务，可用 Testcontainers 或 GitHub Actions `services`；
  - ArchUnit 或单元测试增加“列名 / 别名不得为 MySQL 保留字”的检查。

### 2.2 引用检查扩展点缺失（缺陷，第一批已处理）

> **已处理**：各模块在 `config/<Module>ReferenceConfig` 中注册实现，只查本模块的表：
> - `SalesOrderReferenceChecker`：生产（未作废的生产订单）、出货（出货通知）、财务（收款单、应收单）；
> - `CurrencyReferenceChecker`：财务（应收 / 应付 / 收付款 / 凭证）、销售（订单、报价）、资材（采购订单）；
> - `OrgReferenceChecker`：全部业务模块，框架类 `ModuleOrgReferences` 自动检查本模块单据头的 `org_id` / `dept_id`，外加客户、供应商、仓库、工作中心等主数据的部门字段；
> - `CustomerReferenceChecker`：补充研发工程（样品、项目、工装、ECN）、出货、财务、品质；
> - `MaterialReferenceChecker`：补充品质、出货、财务。
>
> 集成测试 `ReferenceCheckIntegrationTest`。以下为处理前的核对结果。


各模块的 `-api` 定义了引用检查扩展点。下表为核对结果：

| 扩展点 | 用途 | 应实现方 | 现状 | 风险 |
|---|---|---|---|---|
| `SalesOrderReferenceChecker` | 被引用的销售订单不能反审核 / 作废（SAL-SO-R08） | 生产、出货、财务、PMC | **无任何实现** | 已有生产订单、出货通知、预收的订单仍可反审核，下游单据悬空 |
| `CurrencyReferenceChecker` | 已有金额数据时不能修改本位币（SYS-CUR-R03） | 财务、销售、资材等 | **无任何实现** | 有业务数据后仍可修改本位币，全部本位币金额失真 |
| `OrgReferenceChecker` | 删除组织前检查业务数据引用（SYS-ORG-R07） | 各业务模块 | **无任何实现** | 被单据引用的部门可被删除，数据权限与报表归属丢失 |
| `CustomerReferenceChecker` | 有业务数据的客户不能删除（CRM R09） | 销售、研发工程（样品）、出货、财务、品质 | 仅销售实现 | 仅有样品、客诉、应收的潜在客户可被删除 |
| `MaterialReferenceChecker` | 物料停用、删除、改库存管理方式前检查 | 各使用物料的模块 | 仓库、资材、销售、生产已实现；品质、出货、财务未实现 | 仅被检验标准或出货单引用的物料可被删除（风险较低） |

### 2.3 安全默认值（缺陷，第一批已处理）

> **已处理**：
> - 启动时检测 `admin` 仍为初始密码 `admin123` 则置为“下次登录必须改密”（`erp.security.force-default-password-change`，默认开启；不改历史迁移脚本）；
> - `mysql` profile 下 JWT 密钥为开发默认值时拒绝启动；
> - 参数类型新增 `SECRET`：AES-GCM 加密存储（密钥取 `ERP_SECRET_KEY`，为空时由 JWT 密钥派生），页面只显示后 4 位；`ai.api-key` 改为 SECRET，已有明文值启动时自动加密。


- **`admin` 不强制改密**：`system/V2__step1_base_data.sql` 把 `admin` 的 `must_change_password` 置为 0，初始密码 `admin123` 可以一直使用。建议置为 1（首次登录强制修改）。
- **JWT 默认密钥兜底**：`application.yml` 中 `ERP_JWT_SECRET` 有开发用默认值。非 Docker 方式部署时忘记设置也能启动，令牌可被伪造。建议 `mysql` profile 下检测到默认密钥时拒绝启动。Docker 部署已由 `deploy.sh` 自动生成随机密钥。
- **AI API Key 明文存储**：`ai.api-key` 以明文保存在系统参数表，“系统参数”页面可见（需求要求加密存储，只显示后 4 位）。建议参数类型增加 `SECRET`，加密存储、页面脱敏；或只允许环境变量注入。
