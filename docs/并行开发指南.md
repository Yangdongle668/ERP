# 并行开发指南

本项目按模块隔离，目的是让多个开发窗口（多人或多个 Claude Code 会话）**同时开发不同模块**，各自提 PR 合并到 `main`，互不冲突。

## 1. 为什么可以并行

| 容易冲突的地方 | 本项目的处理 |
|---|---|
| Maven 模块注册（根 pom、erp-server pom） | 骨架已一次性注册全部 13 个模块，开发时不需要改 |
| 数据库迁移版本号 | 每个模块独立的 Flyway 目录和历史表，版本号互不影响 |
| 前端路由和菜单 | `src/modules/<code>/index.ts` 自动发现，不需要改公共路由文件 |
| 错误码 | 每个模块独立号段 |
| 表名 | 每个模块独立表前缀 |
| 编码规则初始化数据 | 模块自己声明 `CodeRuleDefinition` Bean，不需要改系统管理的脚本 |
| 模块间调用 | 只通过对方 `-api` 中的接口/事件；未实现的接口先有占位实现，调用方可以先写代码 |

## 2. 每个窗口的工作范围

一个窗口负责一个模块时，**只允许修改**：

```
erp-modules/erp-module-<code>/**          后端（api + biz + 迁移脚本 + 测试）
erp-ui/src/modules/<code>/**              前端
erp-server/src/test/java/com/erp/it/<code>/**   本模块的集成测试（按模块建子包）
docs/requirements/<编号>-<模块>/           需求澄清（如有）
```

**不要修改**（需要改时单独提“公共变更 PR”，见第 4 节）：

- `erp-framework/**`
- 根 `pom.xml`、`erp-modules/pom.xml`、`erp-server/pom.xml`
- `erp-server/src/main/**`
- `erp-ui/src/` 下除 `modules/<code>/` 以外的文件
- **其他模块**的任何文件，包括它们的 `-api`

## 3. 模块之间的契约

### 3.1 我需要调用别的模块

1. 先看对方 `-api` 里有没有需要的接口。
2. 有：直接注入使用。对方还是占位实现（抛出“功能尚未实现”）时，你的单元测试用 Mockito mock 该接口，集成测试可以暂时跳过这条路径。
3. 没有：**不要自己去改对方模块**。提一个“契约 PR”，只在对方 `-api` 中新增接口/DTO + 在对方 `apiimpl` 中加占位实现，合并后双方各自开发。
4. 在自己 biz 的 `pom.xml` 中添加对方 `-api` 的依赖（只能是 `-api`）。

### 3.2 别的模块需要我的数据

- 新增接口、新增 DTO 字段：可以直接在自己的 `-api` 中添加（向后兼容）。
- 修改/删除已有接口或字段：属于破坏性变更，先全局搜索调用方，在同一个 PR 中同步修改调用方，并在 PR 描述中说明。

### 3.3 事件

- 事件类定义在**发布方**的 `-api` 中，监听方依赖发布方的 `-api`。
- 监听方需要新事件时，与发布方约定后由发布方添加（可以用契约 PR）。

## 4. 公共变更 PR

以下改动影响所有模块，必须单独提 PR，**尽快合并**，其他窗口合并后 `git merge main` 同步：

- 框架层新增能力（如数据权限拦截、导入导出工具、审批流引擎接口）
- 修改 `erp-common`
- 新增依赖版本
- 修改全局配置

建议安排：**先合并公共能力，再开启模块开发**。模块开发期间框架层尽量只增不改。

## 5. 推荐开发顺序与分组

依赖关系决定了哪些模块可以同时开始：

| 批次 | 可同时开发 | 说明 |
|---|---|---|
| 第 1 批 | 系统管理（用户/角色/组织/字典）、研发工程（物料类别/BOM）、仓库（仓库/库存过账）、CRM（客户）、资材（供应商） | 基础数据与核心契约，其他模块依赖它们 |
| 第 2 批 | 销售、采购订单与到货、品质（IQC）、生产（生产订单/领料） | 依赖第 1 批的 api |
| 第 3 批 | PMC（MRP）、出货、财务、工作台 | 依赖第 2 批的数据和事件 |
| 第 4 批 | BI/AI | 依赖全部业务数据 |

同一批次内的模块可以完全并行。后一批可以提前开始（面向接口 + mock 开发），但集成测试要等依赖的模块合并后再补全。

## 6. 分支与 PR 规范

- 分支名：`feat/<code>-<功能>`，如 `feat/inventory-stock-posting`、`feat/sales-order`。
- 一个 PR 只做一个模块的一个功能点，便于评审和回滚。
- 提 PR 前本地必须通过：
  ```bash
  mvn -B verify                 # 编译 + 全部测试 + 模块边界检查
  cd erp-ui && npm run build    # 类型检查 + 构建
  ```
- CI（`.github/workflows/ci.yml`）会再次执行以上检查，红灯不得合并。
- 合并前 `git merge main`（或 rebase）并重新跑一遍检查。

## 7. 给每个开发窗口的启动提示词（模板）

开一个新窗口开发某个模块时，可以直接用下面的提示词：

```
你负责开发 ERP 的【<模块中文名>】模块（code=<code>）。
1. 先阅读 CLAUDE.md、docs/并行开发指南.md、docs/architecture/后端架构设计.md、
   docs/requirements/00-总体需求与通用规范.md、docs/ui/UI设计规范.md，
   以及 docs/requirements/<编号>-<模块>/ 下的 README.md 和本次要实现的功能点文件。
   涉及库存的业务单据通过 InventoryDocApi 生成仓库单据草稿；审批调用 WorkflowApi；
   待办/消息/预警调用 NotifyApi。
2. 参考 erp-module-engineering 中“物料”的实现方式（Controller/Service/Mapper/VO/迁移脚本/集成测试）
   和前端 erp-ui/src/modules/engineering/ 的物料页面。
3. 本次实现：<功能点，如“客户档案 + 联系人 + CustomerApi 真实实现”>。
4. 只修改 erp-modules/erp-module-<code>/、erp-ui/src/modules/<code>/ 和
   erp-server/src/test/java/com/erp/it/<code>/，不要改其他模块和框架。
5. 完成后运行 mvn -B verify 和 npm run build，全部通过后提交并创建 PR。
```

## 8. 冲突时怎么办

- 两个 PR 改了同一个模块：后合并的一方 `git merge main` 解决冲突；迁移脚本如果版本号撞了，把自己的脚本改成下一个版本号（未合并的脚本可以改名）。
- 两个 PR 都需要改框架：拆出公共变更 PR 先合并。
- 发现别的模块的 bug：不要顺手改，提 issue 或告知负责该模块的窗口。
